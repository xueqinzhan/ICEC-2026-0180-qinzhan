### 项目四官方原文与分值

> **目标**：针对校园真实高频痛点（通知提取、器材借还核对、错题归档等）在 AI 辅助下开发可运行的实用工具并投入日常使用。
>
> **必交 GitHub 过程数据（防摆拍要求）**
> ① 连续不少于 7 天的程序自动化运行日志（Telemetry Logs，含脱敏时间戳、调用频次、耗时与报错记录，每日同步至 `process_logs/`）— **25 分**
> ② 基于日志的至少 3 次 Git 迭代 Diff 记录 — **20 分**
> ③ 完整源码与 8 位真实用户使用反馈 — **15 分**

**材料要求**：个人电脑 + 连续 7 天真实运行日志。无需借用工坊硬件，这是我当时能独立完成的唯一约束条件。

### 为什么选项目四

1. **唯一不依赖专用硬件的项目**。项目一/六/七需要 ESP32、传感器、光伏板，项目二需要 200 张自拍数据集，项目五要拆电器。我当时只有个人电脑，项目四的材料清单我全齐。
2. **手上已经有真实痛点数据**。阶段一课题03 刚测完 24 组校园 WiFi 信号，痛点是现成的，不需要另外找场景。
3. **和后续方向最接近**。项目四的英文官方名是 *"Campus Utility Software / **Agent** & 7-Day Telemetry Verification"*，交付物本身就允许是 Agent。我学的是人工智能技术应用、主攻智能体方向，项目四是 8 个里唯一能把"软件工具"往 Agent 演的方向做的。

### 为什么 WiFi 盲区算"校园真实高频痛点"

官方给的示例是通知提取、器材借还、错题归档，没提 WiFi。我的理由是：

- **高频**：全校学生每天反复选座、找信号，宿舍/楼梯/机房是刚需场景，不是一次性问题
- **真实**：不是我推测的，是我在 431 走廊实测到下载只有 3.9 Mbps（见现场照片 `wifi_431_corridor_1.jpg`）时自己也遇到了
- **可量化**：痛点能被 dBm / ms / Mbps 精确描述，符合考核"凭实测数据核验"的导向

## 与阶段一课题03 的关系：同一批数据，不是同一件工作

这一点必须主动说清楚，否则容易被当成拿一份数据交两次。

**数据源确实相同**——阶段一的 24 组 WiFi 实测（8 点位 × 3 轮，2026-10-22，iPhone 15 Pro + Wi-Fi Analyzer）就是阶段二 app 内置的数据。这是刻意延续，不是省事：**课题03 的交付要求本身就止步于"提交原始数据与照片、分析衰减规律"，我测完得到的只是一张没人看的 Excel。** 阶段二解决的问题正是"数据躺在表里，同学到了楼梯间还是不知道网为什么差"。

| | 阶段一 · 课题03 | 阶段二 · 项目四 |

## 日志暴露出来的真问题（不是我预设的）

这部分比"做了什么"更有价值，全部来自日志本身：

1. **`point_detail_view` 只出现 4 次，其中 3 次是我自己测的** → 同学根本没在看测量点详情
2. **4 位同学的操作序列终结在 `pageAdd`，却没产生任何 `point_added`** → 添加流程有阻碍，可能是表单校验或不懂要填什么
3. **3/5 的用户只切了 1~2 个标签就退出** → 工具的实际价值尚未验证
4. **原计划 8 份反馈，实收 5 份** → 纯前端无法自动回收数据，靠人工催办不可规模化
5. **10-27 一天完全漏记** → 我没有回补，如实保留

结论：**当前形态解决了"数据没人看"，但还没解决"看了有用"。** 这五条已如实写进提交材料的"尚未解决的缺陷"。

## 与后续方向（智能体）的衔接

项目四官方英文名 *Campus Utility Software / **Agent*** 已把 Agent 列为可交付形态。阶段二跑通的是"采集 → 清洗 → 工具化 → 埋点验证 → 迭代"的完整链路，但采集环节仍靠人工。下一阶段计划把智能体接入两处：

- **自动采集录入**：用 Agent 调用测量脚本、直接写入数据源，替代"手抄 56 组 / 现场测 24 组"
- **信号问题诊断问答**：把 24 组实测数据 + 衰减规律作为知识源，让 Agent 回答"我这儿网差是为什么、该报修还是该换位置"
