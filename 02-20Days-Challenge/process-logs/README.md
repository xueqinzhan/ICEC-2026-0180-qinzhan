# 日常运行日志汇总

项目四要求「连续 7 天日常运行日志验证」。原始日志文件位于
[`../Campus-WiFi-Map/process_logs/`](../Campus-WiFi-Map/process_logs/)，本目录只做汇总与口径说明。

采集方式：app 内置 `TelemetryLogger` 自动埋点 → 存 localStorage → 每日手动导出 JSON → 归档入库。

## 四、日志暴露出来的真实问题

这些结论是从日志里读出来的，不是主观判断：

1. **核心功能几乎没人用**。`point_detail_view` 全量只有 4 次，且 3 次来自开发者自己，1 次来自唯一那位深度使用的同学。5 位同学中有 3 位（OPPO、Vivo、华为）打开后只切了 1 次标签就退出，停留最短的一次只有 524ms。**说明工具对他们没有形成有效使用，"地图 + 详情"这个主价值路径没跑通。**

2. **`tab_switch` 占比异常高（195/417 ≈ 47%）**。大量操作是漫无目的地来回切标签，而不是带着目的去查某个点位的信号。这是典型的"不知道这东西能干啥"的行为特征。

3. **多人停留在「添加测量点」页后中断**。4 位用户的会话终点都是 `pageAdd`，但没有产生一条 `point_added` 记录——他们打开了录入表单，然后放弃了。推测是移动端表单字段过多（含 X/Y 百分比坐标，普通同学不知道该填什么）。

4. **反馈计划 8 份，实收 5 份遥测**。反馈表依赖浏览器下载 JSON 文件，部分手机浏览器下载失败或同学嫌麻烦未回传。

## 五、若要继续改进，优先级排序

| 优先级 | 改动 | 依据 |
|-------|------|------|
| P0 | 砍掉「添加测量点」的手动 X/Y 坐标输入，改为在平面图上直接点击取点 | 4 位用户卡在该页面且零转化 |
| P0 | 首屏直接给结论（"哪几个位置信号差"），而不是先展示地图 | `point_detail_view` 仅 4 次，说明用户不会主动探索 |
| P1 | 反馈改为表单页内提交 + 生成可复制文本，不依赖文件下载 | 8 份计划实收 5 份 |
| P1 | 埋点补充 `dwell_time_per_tab`，量化每个标签的停留 | 现在无法判断用户在哪一页流失 |
| P2 | IDW 稀疏区改为不渲染并标注「无实测数据」 | 避免热力图给出无依据的渐变 |
